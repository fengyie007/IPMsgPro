# Rust 第二阶段计划：图片收发与截图

## Context
第一阶段已提交为 `89ce454`：Rust + Tauri 2 核心预览版，包含真实文本通信、分组通讯录、历史、配置和托盘。Windows UDP 10054接收中断及同名多端点覆盖已修复；27个单元测试、8个UDP集成测试、桌面cargo check和前端类型检查通过，最新实机日志确认发现与消息收发恢复。

**执行状态：用户已授权开始；本轮仅实施2A图片接收与历史，2B图片发送和2C截图尚未开始。** 推荐只补齐图片/截图这条完整使用链路，避免同时移植文件传输、扫描、通知而扩大风险。所有实现仍限定在 `tauri-rust/`，不改旧C++版本及其数据。

## 阶段目标与非目标

目标：Rust版能接收飞秋/C++版的内嵌图片并直接预览；能选择PNG/JPEG/BMP发送；能截图、标注后以图片发送；重启可看图片历史；失败、重传和退出不损坏现有文本通信。

不包含：TCP普通文件收发、文件/文件夹拖放、IP范围扫描、高级通知/声音、GIF动画、图文/多图混排、加密协议、旧版数据自动导入、多网卡联系人自动聚合。普通文件按钮仍禁用，不以文件通道冒充图片发送。

## 推荐顺序与验收门槛

### 2A. 先完成图片接收和历史（建立协议基线）
1. 在 `crates/ipmsg-core/src/image/` 新增纯Rust `lzw`、`dib`、`fragments` 模块，与Tauri/窗口分离。
2. 以父目录 `src/util/feiq_lzw.*` 和 `飞秋扩展协议已验证.md` 为依据：
   - `LZW! + uint32LE DIB长度 + uint32LE CRC32 + 压缩流`；DIB不含BMP文件头。
   - 字典256～4095循环覆盖、码宽停在12位、正确的位序/增长时机，以及循环后的KwKwK特例。
   - 长度、CRC、尺寸、stride、压缩类型和实际像素边界必须验证；不再裁高度掩盖坏数据。
3. `network.rs` 将0x2000C0图片分片交给有界拼接器，而非当前“不支持图片”提示分支；0xC1逐片ACK。按**已解析的端点联系人ID+wire图片ID**隔离，正确处理乱序、重复、缺片和冲突。
4. 使用明确的接收状态 `collecting → finalizing → completed/rejected`。解码、文件写入和数据库提交在后台处理，不能堵塞UDP接收或持锁等待；形成完整图片的那个分片仅在校验、写盘和记录成功后确认。失败状态要保留拒收语义，防止末片重传被误ACK为成功。
5. 图片保存在独立数据目录的图片子目录，使用内部assetId生成路径，禁止对端路径、覆盖既有文件。SQLite增量增加图片元数据，保留原有文本与去重记录；旧“不支持图片”提示不自动改写，不让它的ID误挡真实图片消息。
6. 更新 `Message/HistoryRecord` 的可选图片元数据、`MessageBubble`、历史加载和列表预览，显示缩略图、点击查看原图，不把base64整图长期写进SQLite。
7. 图片与引用以端点+wire图片ID关联，只形成一条图片历史。引用先到时只登记有界等待状态、按SENDCHECKOPT回复引用回执，不落一条额外文本；图像先完成时即可持久化和展示，后来或重复引用仅确认，不重复入库。**最终分片ACK不得等待引用，否则与数据先行发送器死锁。** 只有引用而无数据的等待状态120s后失败/清理；只有完整图片而没有引用仍保留一条图片消息。识别引用后必须绕过旧“不支持图片”提示和普通文本分支。

验收：飞秋→Rust、C++→Rust、Rust重启历史预览；同ID跨端点不混图、重复片不重复消息；损坏/截断/过大图片不显示为成功。JPEG/PNG原始载荷可按既有接收实现兼容，但必须单独做格式验证，不能将未测试格式一概标成互通通过。

### 2B. 再完成图片选择与发送
1. 在 `src-tauri/src/image.rs` 增加受控图片选择/导入及预览：原生单选PNG/JPEG/BMP，内容解码确认格式，透明PNG按白底合成为24位bottom-up DIB。图像转换使用Rust图像库，原生选择器通过Tauri对话框能力，不调用旧exe/DLL。
2. 复用2A的编码/校验模块，在后台编码；core新增图片发送队列，沿用单socket和现有取消/退出管理。
3. 二进制包单独编码，不能走会转换GBK的文本body接口；512字节分片、范围校验、按已确认片数计算进度、有限重试、错误来源/ID/片号确认不推进状态。
4. **固定已验证顺序：先收齐图片所有分片ACK，再发一次0x120聊天引用并等RECVMSG。** 引用保持 `/~#>id<B~`、合法字体尾标和两个NUL；重试沿用同一包号，不发第二条引用“刷新预览”。保留10054等可恢复UDP错误的继续接收逻辑。
5. 状态区分排队、编码、传输、等待引用确认、完成、失败/取消。只有所有必要确认完成后才标记送达；不表示已读或已渲染。取消只终止本地任务，不宣称撤回对端已收到的消息。
6. 前端图片按钮、发送前预览确认、进度和失败提示复用旧前端交互，但不恢复旧的TCP `sendImage → file.send` 链路。以messageId缓冲早到事件、终态不能被迟到进度覆盖。

建议IPC（继续走现有ipmsg_command/ipmsg-event封装）：
- `image.select`：原生选择并导入，返回内部assetId、文件名、尺寸、字节数、预览信息；取消不是报错。
- `image.send {target, assetId}`：返回稳定messageId与独立的8位wire图片ID，成功返回仅表示接纳任务。
- `image.read {assetId}`：只能读取已导入/已入库的应用图片，不能接受任意磁盘路径。
- `image.cancel {messageId}`：取消未终结任务；`image.send_progress/completed/failed` 更新状态。

初始资源限制与C++保持同量级：原文件20MiB、1600万像素、DIB64MiB、压缩载荷16MiB；限制并行编解码、队列/拼接数量、总在途资源及超时，不能只限制单图大小。默认32片窗口、约2ms间隔，普通窗口1s确认等待、首发加最多3次重发；这是实现策略，不是协议定律。

最终窗口需覆盖接收端解码/写盘/入库时间，单独给30s预算（约2s重试一次，最多15轮），总发送任务不超过120s；接收finalizing目标期限25s。finalizing中的重复片不启动第二个解码任务，也不提前确认被挂起的完成片；处理成功后补ACK。completed/rejected状态至少保留10分钟、设置数量上限，额度不足拒绝新任务，不提前遗忘失败状态来换容量。超时后台任务即使稍后结束也不得再发布成功；慢盘用例必须验证这一约束。

验收：Rust→飞秋实际直接显示完整图片，而不是“可双击图标”；Rust↔Rust及Rust↔C++兼容；中文路径、透明图、复杂大图、字典多次循环；慢接收/丢片时文本仍可正常通信。

### 2C. 最后接入截图与标注
1. 复用父目录 `frontend/src/components/ScreenshotEditor.tsx` 的选区、矩形、箭头、画笔、马赛克、撤销等前端逻辑；不直接搬旧窗口置顶调用。
2. 截图平台实现在 `src-tauri/src/capture.rs`，优先使用已有windows-sys能力和Rust图像编码；只捕获主窗口所在显示器，暂不做跨屏拼接。
3. 使用独立截图编辑窗口承载全屏编辑。临时置顶只属于该窗口，不改变主窗口置顶状态；对物理像素、DPI缩放和负坐标明确换算。
4. 流程为隐藏主窗口→后台捕获→显示编辑窗口→确认后生成受管图片assetId→复用image.send；取消、关闭、初始化失败及发送失败都关闭编辑窗口并恢复主窗口。退出应用时不能再强行恢复主窗口。
5. 截图会话只能有一个，重复点击受控；截图窗口只允许当前会话的读取/确认/取消命令，不能因新增窗口开放全部历史/文件/网络IPC。

验收：确认发送、Esc取消、关闭编辑器、捕获失败、发送失败后均不残留置顶或隐藏窗口；100%/150%缩放、双屏负坐标及中文输入标注正确。

## 稳定性、安全和兼容性约束

- 保留阶段一的端点ID、临时端口唯一匹配、早到ACK、历史清空边界及Windows UDP恢复测试，不退回只按username@hostname识别联系人。
- 通过数据库schema版本迁移增加图片元数据，不重建或清空文本历史；assetId与线上8位imageId分开。
- 先落盘/入库再通知完成；图片与文本的去重、清空、历史加载边界一致。暂不实现激进的自动图片GC，避免误删被历史引用的文件；取消产生的未引用临时资产单独有界清理。
- 原生选择/导入生成内部assetId，预览与打开仅限应用受管图片；限制读取/解压/尺寸和并发。只为主窗口与截图窗口开放各自需要的操作，不授予全盘读写或任意shell权限。
- core接收线程只解析/路由和短时更新状态，编解码/磁盘IO通过有界后台任务处理，锁不跨await；退出取消并等待任务，有超时和终态。
- 能力按里程碑分别启用：新增 `imageReceive`、`imageSend`，现有 `images` 兼容汇总标记仅在完整收发可用时开启；`screenshot` 在2C通过后开启。不能仅将一个布尔值设为true而留下假成功入口。
- 新依赖初选 `image 0.25`（仅png/jpeg/bmp，关闭无关默认格式）及 `tauri-plugin-dialog 2`，截图优先沿用windows-sys；本机可见image 0.25.10和dialog 2.7.2源码缓存，但不等于所有传递依赖都齐全。
- 依赖仍优先离线解析和测试；缺少新依赖先报告，不自动联网升级。保留真实生成的Cargo/npm锁文件。

## 测试与交付标准

1. Rust单测：CRC、DIB边界/行对齐、LZW码宽与循环/KwKwK、分片乱序/重复/丢失/冲突、多端点同ID、完成/拒收/取消状态。
2. 交叉验证：使用现有C++编解码器及已验证原始样本检验Rust输出，不只做新编码器与新解码器互相验证。将可公开的合成图作为固定测试材料，不默认提交用户抓包/图片。
3. UDP集成：正确与错误来源ACK、有限重传、坏图不最终确认、引用必须晚于全部分片确认、接收10054后继续服务、任务退出不死锁。
4. 存储/前端：旧数据库迁移、图片历史重载、早到事件、同尺寸不同图片不误去重、清空与收图并发、预览失败/取消不假成功。
5. 实机矩阵：飞秋、原C++版、新Rust版双向图片；最终以接收端直接预览和原图内容为准，而非仅看sendto/ACK。
6. 自动检查延续已授权范围：离线cargo fmt/check/test、前端完整类型与状态测试。不自动启动GUI或打包；截图和原生窗口行为由用户实测验收。

交付按2A→2B→2C独立完成和提交；每一步通过后再解锁下一步，记录已测/未测，不将全部功能一次性标为完成。
